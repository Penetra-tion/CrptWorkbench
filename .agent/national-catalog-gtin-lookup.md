# Реализовать поиск собственных карточек Национального каталога по GTIN

Этот ExecPlan является живым документом. Разделы `Progress`, `Surprises & Discoveries`, `Decision Log` и `Outcomes & Retrospective` обновляются по мере выполнения. Документ ведётся по правилам `.agent/PLANS.md`.

## Purpose / Big Picture

После изменения оператор сможет в API Console выбрать Национальный каталог, ввести один GTIN и получить сведения о собственной карточке: наименование, статус, ТН ВЭД, товарную группу, все уровни упаковки и разрешительные документы. В mock-режиме сценарий останется полностью локальным. В Production приложение будет обращаться только к двум разрешённым методам официального API НК с защищённым Bearer-токеном профиля.

Второй этап добавляет безопасный production-транспорт и хранение составного обмена. Он завершён, когда allowlist пропускает только два точных метода официального хоста, секреты маскируются, а старая база мигрирует без потери истории.

Третий этап добавляет UI и полную проверку. Он завершён, когда обычный режим показывает карточку, документы и упаковки, технический режим показывает каждый обмен, история сохраняет один запуск, сборка и тесты проходят.

## Surprises & Discoveries

- Observation: `/v3/feed-product` возвращает собственные карточки всех статусов, кроме статуса «Требует обработки»; `/v4/rd-info-by-gtin` применим только к опубликованным карточкам.
  Evidence: официальная документация НК, разделы 3.1.1 и 3.3.6.
- Observation: существующий результат операции и история поддерживают ровно один HTTP-обмен.
  Evidence: `IntegrationExchange`, `ApiExecutionResult` и `ApiRequestLog` содержат один набор request/response полей.

## Decision Log

- Decision: сохранить `national-catalog.product` и представить поиск как одну операцию с nullable списком фактических обменов.
  Rationale: избранные операции сохраняют совместимость, а опубликованная карточка может требовать второго запроса.
  Date/Author: 2026-09-23 / Codex.
- Decision: итоговый `ResponseBody` операции будет типизированным нормализованным JSON, а сырые ответы останутся в маскированном списке обменов.
  Rationale: Razor не должен разбирать внешний протокол, при этом техническая диагностика сохраняется.
  Date/Author: 2026-09-23 / Codex.

## Context and Orientation

Операции описаны и выполняются в `src/CrptWorkbench.Application`; внешние адаптеры находятся в `src/CrptWorkbench.Clients`; DI и Blazor UI находятся в `src/CrptWorkbench.Web`; SQLite и миграции находятся в `src/CrptWorkbench.Infrastructure`. Mock является режимом по умолчанию. Bearer-токен НК уже хранится через `ISecretStore` под ключом профиля и никогда не возвращается в UI.

## Plan of Work

Добавить модели результата и обработчик Национального каталога в Application. Обработчик валидирует GTIN, получает Bearer только для production-клиента, вызывает карточку, разбирает внешний JSON и для опубликованной карточки запрашивает документы. Он нормализует статусы, уровни упаковки, ТН ВЭД и товарную группу по справочнику документации.

Добавить production-клиент в Clients на именованном `HttpClient`, который отключает redirects и проходит отдельный allowlist для точных путей `/v3/feed-product` GET и `/v4/rd-info-by-gtin` POST на официальном HTTPS-хосте. Mock-клиент формирует контрактные ответы локально.

Расширить доменный обмен, результат выполнения и историю nullable списком обменов. В SQLite хранить маскированный JSON в новом nullable столбце; старые строки остаются допустимыми. UI читает нормализованный результат и выводит карточку, документы и упаковки, а в техническом режиме перечисляет все обмены.

## Validation and Acceptance

При GTIN длиной 8, 12, 13 или 14 цифр mock-поиск показывает заполненную карточку, несколько уровней упаковки и документы. Ведущие нули сохраняются. Для опубликованной карточки список технических обменов содержит два элемента; для черновика — один. Ошибки 401, 403, 404, 429 и 5xx получают понятные сообщения. Ни один настоящий запрос не выполняется в mock-режиме.

Production allowlist отклоняет другой хост, HTTP, другой порт, userinfo, fragment, лишний путь и неверный метод. В истории сохраняется одна строка с общим correlation ID; Bearer замаскирован и отсутствует в базе в открытом виде.

## Idempotence and Recovery

Изменения кода и миграция повторяемы через обычную сборку и запуск миграций. Новая колонка nullable, поэтому существующие записи не требуют преобразования. При сбое дополнительного запроса документов карточка остаётся успешным частичным результатом с предупреждением.
